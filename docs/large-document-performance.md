# 大文档性能优化与验证

这次工作优先减少重复启动、屏外资源渲染和输入期间的全文辅助计算。保留完整 Markdown 文本、现有文档会话和历史机制，不引入按字符串截断文档的渲染路径。

## 已实现的预算

沿用 `src/foundation/largeDocument.ts` 的综合压力判断（字节、行数、表格、图片、公式和图表），不另设一套互相冲突的大小阈值。

| 场景 | 行为 |
| --- | --- |
| Source / Live 启动 | 大文档不在后台预加载完整 Preview；进入 Preview 时再渲染当前文本 |
| 大文档 Source | 使用现有 Lezer 语法树和基础配色，跳过全篇 TextMate token 预热；着色精细程度与普通文档不同 |
| Preview 首次启动 | 隐藏的文本与历史载体使用 Source，保留用户上次选择的编辑模式，切回时再应用 |
| Mermaid | 大文档不预热全文图表；Preview 仅渲染接近视口的块，滚动或展开折叠区域时继续处理 |
| Preview 公式 | 接近视口才创建尺寸控制器，离开后暂停 resize/font 测量，保留已拟合的 DOM 和几何；隐藏整个 Preview 时也暂停 |
| Preview 表格 | 接近视口才做列宽测量，并只观察附近表格的宽度变化；嵌套的 Live HTML 表格保留原有逻辑 |
| Live 输入辅助 | 大文档输入期间暂停悬浮块标题的全文发现；普通正文输入只映射已知公式结果，编辑已知公式仍保留每个有效结果 |
| 全文扫描 | 公式扫描直接寻找下一个 `$`；数学与 HTML 区间查询使用有序索引，避免每个节点/每行逐一检查全部区间 |
| 虚拟块高度 | 同一同步计算中复用相同字体和文字的宽度；微任务结束即清空，避免字体加载后使用旧结果 |

`performance.largeDocumentOptimization` 仍控制初始模式偏好，手动模式选择继续优先。上述资源预算属于各展示功能的执行策略。压力判断在编辑器创建时确定；从小文档持续增长为大文档的会话还不动态切换 Source 着色策略。

## 验证方式

新增 `bun run test:large-document-budget`，已纳入 quick 与 release 门禁。它使用实际生产 Webview、真实预览渲染器和隔离无头浏览器，检查：

- Source 启动不请求隐藏的完整预览，正文可以输入和撤销。
- 远处的公式、Mermaid 和表格不提前创建或测量。
- 滚动到远处后，这些块确实完成展示。
- 离开公式区域后，尺寸监听暂停。

另有随机区间差分检查、含长正文前缀的公式边界检查、已知公式的无效输入与整块替换检查，以及字体指标改变和虚拟块滚动检查。

第一轮验证结果（提交 `b6756acb`）：

- Webview 与扩展生产构建完成，TypeScript 检查通过。
- 完整 quick 门禁通过：66/66 条命令，976 秒。报告：`.local/test-runs/1792248258622-6150cf05/report.json`。
- 架构约束检查、测试登记检查及 `git diff --check` 通过。
- 补充浏览器检查通过：`test-preview-mermaid-runtime`、`test-preview-table-layout-production`、`test-live-input-path-production`、`test-html-content`、`test-math-tag-layout`。数学排版检查保留 420px/1280px、明暗主题、四种展示/导出路径与打印准备断言；Source 窄窗的入口条件见文末说明。
- 验证范围为隔离无头浏览器和仓库合同测试，未执行完整 release/endurance，也未在 VS Code 原生窗口逐项验收。

综合人工样本约 1 MiB、30,000 行，覆盖本地图片、表格、公式、HTML、折叠区、代码与 Mermaid 等。它属于高密度压力样本，不能用字节数直接类比纯文本文件。诊断采样使用生产构建，分别记录首屏、长任务、输入、撤销和堆使用；无头浏览器采样不等于 VS Code 原生窗口端到端验收，也不代表全篇每个编辑位置均已覆盖。

### 本机综合样本对照（2026-10-17）

从同一 Git HEAD 的源码另行构建修改前版本，使用相同依赖、1100×720 视口、隔离 Chromium 配置与同一个 1,048,576 字节样本。下表为冷启动诊断采样，计时从收到初始化文本到展示面已出现；不是多次运行的分位数或跨设备性能承诺。

- 修改前源码：`dc1c68d19d27a2791851209fcd25c92a0273826b`。
- 样本：`large-markdown-comprehensive-1MiB.md`，SHA-256 `c37b87bb38e6abfb2a75bcd37e335d8f4911d28855c24be4b5110f10057e3c64`；30,788 行、31 类格式、514 处图片引用、241 个 Mermaid fence（含 1 个故意无效的例子）。

| 模式 | 修改前首屏 | 修改后首屏 | 观察 |
| --- | ---: | ---: | --- |
| Source | 4,171 ms | 219 ms | 隐藏 Preview 的全文请求从 1 次变为 0 次 |
| Live | 10,250 ms | 2,717 ms | 隐藏 Preview 的全文请求从 1 次变为 0 次 |
| Preview | 11,492 ms | 5,810 ms | 隐藏编辑器从 Live 改为 Source；仍生成完整预览 DOM |

Source 独立复测为 217–223 ms。修改后 Preview 的几次采样为约 3.5–5.8 秒，存在明显波动。采样中 Source 的最长主线程任务约 123 ms；Live 仍约 1 秒，Preview 后续仍出现超过 2 秒的长任务，因此 **250 ms 响应预算尚未全面达到**。

尾部正文连续输入 5 个 ASCII 字符的整段自动化耗时约 Source 533 ms、Live 625 ms；对应一次撤销约 246 ms、1,267 ms。这包含多个键盘事件及检查开销，不能当作单字符 input-to-paint 延迟，也没有充分的前后输入延迟对照。它表明首屏优化有效，但尚不能宣称极端样本下持续编辑与撤销已完全流畅。

本地原始 JSON / CPU profile 位于 `.local/large-document-results/`（`original-full-*`、`final-startup-*`、`final-live-*`、`final-preview-alone-*`）。压力诊断的 250 ms 断言仍会失败，这与正确性回归是否通过是两组不同证据。

## 第二轮：原生验收与顺序扫描

第一轮作为独立提交保留。第二轮使用 VS Code 1.138.0 的独立用户配置、独立扩展目录和开发扩展宿主，分别打开约 7 KB 的混合文档与综合样本副本。综合样本只在副本前加了固定编辑目标；图片资源也复制到测试工作区。

原生验收通过的项目包括 Source/Live 的五次输入、撤销、精确重做、中文组合提交、保存后磁盘内容与宿主文档一致，以及 Preview 图表、滚动到底和切回 Source。原始样本的 SHA-256 保持不变。中文通过 Electron 的 CDP IME composition/commit 事件路径提交并检查只出现一次；这没有覆盖 Windows 拼音输入法的候选词窗口。Preview 的滚动验收先发出真实滚轮事件，退出模式切换的阅读位置恢复，再定位图表；单纯调用 DOM 滚动可能被恢复任务覆盖。

最小复现去掉了图片、公式和表格，只保留正文，仍能触发全文辅助扫描。生产 Live 状态字段的一次 5,001 行正文撤销原先产生 **70,011 次随机行查找**。本轮把列表、HTML、标签、脚注、分隔线、备用表格、原始文件链接及冲突标记的完整扫描改成顺序文本遍历，并直接使用已有行文本。无脚注标记的行不再逐个查询保护区间；无 `#` 的行不再计算标签颜色排除范围。不保留按文档大小增长的行缓存。

新增 `test-live-scan-budget.ts` 使用真实生产状态字段验证正文撤销的工作量，同时检查空文档、尾部空行、文本树分支及 UTF-16 位置。修改后同一撤销只剩 **1 次随机行查找**，该测试已加入现有大文档预算门禁。另用第一轮源码做了 100 组混合文档的装饰差分，输入前、输入后和撤销后的位置及装饰类型一致。

相同依赖、相同压缩生产构建条件下，约 754 KB 的纯正文诊断样本单次对照为：首屏约 602 → 420 ms，撤销约 173 → 108 ms，最长心跳间隔约 517 → 351 ms。原始结果为 `.local/large-document-results/phase2-checkpoint-plain-live-30.json` 和 `phase2-final-plain-live-30.json`。这是单次无头采样；两版的 250 ms 阻塞诊断仍失败，不能标为整体性能预算通过。

这只是降低完整扫描的单位成本。原生综合样本的单次 Live 撤销仍约 0.9 秒，没有证据表明这轮已经稳定改善了它的端到端延迟。输入停止后很快撤销的一次采样达到约 1.9 秒；CPU profile 显示输入的延迟刷新与撤销各执行了一次完整装饰重建。把两者分开计时可避免混淆，却不能解决用户遇到的排队等待。`beforeinput` 到两次动画帧的采样也不包含事件排队之前的等待，不能作为完整按键延迟。

原生原始结果与 CPU profile 位于 `.local/phase-two/`，包括 `checkpoint-native`、`sequential-profile`、`final-native` 和 `final-settled-native`。普通文档的交互仍是几十毫秒量级；这些本机单次采样不是跨设备性能承诺。

第二轮验证结果：

- Webview 生产构建、严格类型检查、大文档预算、生产输入路径、复合列表及展示一致性、HTML 内容、渲染内容历史往返、虚拟块滚动、数学编号排版检查通过。
- 表格生产命令和表格历史快捷键的补充检查通过；架构检查及测试登记检查通过。该轮未重新执行完整 quick/release/endurance，第一轮的 66/66 结果不充当第二轮完整门禁结果。
- `test-history-matrix.ts` 在“有未提交单元格编辑时插入行”的行数等待处超时（第 1291 行）。第一轮提交的独立源码副本用相同测试也在同一位置失败，尚未解决；不能将整个历史矩阵标为通过。对照日志为 `.local/phase-two/history-matrix-checkpoint.log`，本轮日志为 `.local/phase-two/check-history-matrix.log`。
- 本轮逐项结果为 `.local/phase-two/verification.json`，最终原生验收为 `.local/phase-two/final-settled-native/result.json`。原生验收通过且原样本未变；综合样本 Live 撤销约 933 ms。

## 明确的剩余范围

Live 仍通过状态字段维护会影响高度的全文块装饰；延迟全文重建会减少与连续输入竞争，但重建本身仍可能产生长任务。Preview 仍一次生成完整 HTML 和 DOM，按需图表和测量不会消除 HTML 解析与全篇 DOM 的成本。极端密度样本的首次 Live/Preview 打开仍可能达到秒级。

下一步若继续降低这部分开销，需要为块装饰做增量失效，并为 Preview 建立块索引及可取消的分批提交。真正的块窗口化还要同时解决高度估计、滚动锚点、跨块选择、查找、复制、无障碍和导出，属于独立的架构阶段；不应通过硬裁文档或单纯增加等待时间实现。

成熟编辑器的官方资料、策略与限制见 [资料核对](large-document-research.md)。

补充数学排版检查在修改前版本也复现了一个独立问题：420px 宽度下 Source 分栏入口可能落在工具栏屏外。因此该排版测试使用“宽窗打开分栏，再收窄窗口”的真实操作路径，仍检查 420px 下所有公式及编号是否放得下；本轮没有修复这个既有的窄工具栏入口问题。
