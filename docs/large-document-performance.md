# 大文档性能优化与验证

这次工作优先减少重复启动、屏外资源渲染和输入期间的全文辅助计算。保留完整 Markdown 文本、现有文档会话和历史机制，不引入按字符串截断文档的渲染路径。

## 已实现的预算

沿用 `src/foundation/largeDocument.ts` 的综合压力判断（字节、行数、表格、图片、公式和图表），不另设一套互相冲突的大小阈值。

当前压力值为 `UTF-8 字节数 / 300000 + 行数 / 8000 + 富内容数量 / 256`，达到 `1` 时使用大文档策略。富内容数量是启发式识别的 Markdown 表格、图片、Mermaid 和块公式数量之和，并非完整语法解析。各项累加，因此这些参考值不是必须单独达到的门槛：例如 150,000 字节、2,000 行、64 个富内容就已达到 `1`。它们是当前基准校准值，不代表所有设备上的精确卡顿边界。

设置中的“大文档优先以源码模式打开”只决定之后打开大文档的初始模式。关闭后沿用原有模式偏好，Source / Live / Preview 的自动性能优化仍按需执行；开启后也可在当前会话手动切换模式。沿用 `performance.largeDocumentOptimization` 配置键和原有布尔值，已有用户无需迁移。中英文设置说明和快捷提示均明确这一范围，搜索“大文档优化”“快速打开大文档”仍可找到该设置。

| 场景 | 行为 |
| --- | --- |
| Source / Live 启动 | 大文档不在后台预加载完整 Preview；进入 Preview 时再渲染当前文本 |
| 大文档 Source | 使用现有 Lezer 语法树和基础配色，跳过全篇 TextMate token 预热；着色精细程度与普通文档不同 |
| Preview 首次启动 | 隐藏的文本与历史载体使用 Source，保留用户上次选择的编辑模式，切回时再应用 |
| Mermaid | 大文档不预热全文图表；Preview 仅渲染接近视口的块，滚动或展开折叠区域时继续处理 |
| Preview 公式 | 接近视口才创建尺寸控制器，离开后暂停 resize/font 测量，保留已拟合的 DOM 和几何；隐藏整个 Preview 时也暂停 |
| Preview 表格 | 接近视口才做列宽测量，并只观察附近表格的宽度变化；嵌套的 Live HTML 表格保留原有逻辑 |
| Live 输入辅助 | 大文档输入期间暂停悬浮块标题的全文发现；普通正文输入只映射已知公式结果，编辑已知公式仍保留每个有效结果 |
| 全文扫描 | 公式扫描直接寻找下一个 `$`；数学与 HTML 区间查询使用有序索引，避免每个节点/每行逐一检查全部区间 |
| 虚拟块高度 | 同一同步计算中复用相同字体和文字的宽度；微任务结束即清空，避免字体加载后使用旧结果 |

上述资源预算属于各展示功能的执行策略。压力判断在编辑器创建时执行，内容明显变化时也会在空闲时间复评；当前会话启用后保持该策略，避免反复切换，重新打开时再重新评估。运行时复评不会改变用户正在使用的模式。

- Source 启动不请求隐藏的完整预览，正文可以输入和撤销。
- 远处的公式、Mermaid 和表格不提前创建或测量。
- 滚动到远处后，这些块确实完成展示。
- 离开公式区域后，尺寸监听暂停。

另有随机区间差分检查、含长正文前缀的公式边界检查、已知公式的无效输入与整块替换检查，以及字体指标改变和虚拟块滚动检查。

## 第二轮：原生验收与顺序扫描

第一轮作为独立提交保留。第二轮使用 VS Code 1.138.0 的独立用户配置、独立扩展目录和开发扩展宿主，分别打开约 7 KB 的混合文档与综合样本副本。综合样本只在副本前加了固定编辑目标；图片资源也复制到测试工作区。

原生验收通过的项目包括 Source/Live 的五次输入、撤销、精确重做、中文组合提交、保存后磁盘内容与宿主文档一致，以及 Preview 图表、滚动到底和切回 Source。原始样本的 SHA-256 保持不变。中文通过 Electron 的 CDP IME composition/commit 事件路径提交并检查只出现一次；这没有覆盖 Windows 拼音输入法的候选词窗口。Preview 的滚动验收先发出真实滚轮事件，退出模式切换的阅读位置恢复，再定位图表；单纯调用 DOM 滚动可能被恢复任务覆盖。

最小复现去掉了图片、公式和表格，只保留正文，仍能触发全文辅助扫描。生产 Live 状态字段的一次 5,001 行正文撤销原先产生 **70,011 次随机行查找**。本轮把列表、HTML、标签、脚注、分隔线、备用表格、原始文件链接及冲突标记的完整扫描改成顺序文本遍历，并直接使用已有行文本。无脚注标记的行不再逐个查询保护区间；无 `#` 的行不再计算标签颜色排除范围。不保留按文档大小增长的行缓存。

新增 `test-live-scan-budget.ts` 使用真实生产状态字段验证正文撤销的工作量，同时检查空文档、尾部空行、文本树分支及 UTF-16 位置。修改后同一撤销只剩 **1 次随机行查找**，该测试已加入现有大文档预算门禁。另用第一轮源码做了 100 组混合文档的装饰差分，输入前、输入后和撤销后的位置及装饰类型一致。

相同依赖、相同压缩生产构建条件下，约 754 KB 的纯正文诊断样本单次对照为：首屏约 602 → 420 ms，撤销约 173 → 108 ms，最长心跳间隔约 517 → 351 ms。原始结果为 `.local/large-document-results/phase2-checkpoint-plain-live-30.json` 和 `phase2-final-plain-live-30.json`。这是单次无头采样；两版的 250 ms 阻塞诊断仍失败，不能标为整体性能预算通过。

这只是降低完整扫描的单位成本。原生综合样本的单次 Live 撤销仍约 0.9 秒，没有证据表明这轮已经稳定改善了它的端到端延迟。输入停止后很快撤销的一次采样达到约 1.9 秒；CPU profile 显示输入的延迟刷新与撤销各执行了一次完整装饰重建。把两者分开计时可避免混淆，却不能解决用户遇到的排队等待。`beforeinput` 到两次动画帧的采样也不包含事件排队之前的等待，不能作为完整按键延迟。

## 持续编辑、撤销与资源释放（2026-10-18）

进一步检查发现，输入后的完整展示已经恢复时，结束输入的记账事务又丢弃了屏外装饰，导致块高度二次变化。现改为只在实际文本输入时裁减临时装饰，结束记账保留完整展示。

大文档的普通正文输入另外保留一份完整展示检查点；只有撤销或重做精确回到相同文本、相同选区且展示上下文未改变时才复用。检查点按 CodeMirror 的实际历史分组更新，既覆盖连续输入，也覆盖慢速输入形成的独立历史组。它只保留一份文本与展示，不串联旧 EditorState；解析未完整、语法编辑、模式/选区/配置变化、未知效果和手动块展示状态都保守重建。相同诊断通知不再触发无效事务，但映射后的位置变化仍会更新。

真实编辑器回归覆盖延迟刷新、重复撤销/重做、独立输入组、恢复后远处表格的继续编辑，以及诊断消息和位置更新。独立 VS Code 综合样本验收仍通过输入、中文组合提交、撤销/重做、保存、Preview 图表和滚动检查，原样本未变。本机单次 Live 撤销从前述约 933 ms 降到约 627 ms（`.local/phase-two/history-group-native/result.json`）；仍有明显等待，且该数字不是统计分位数。此轮该次 Preview 冷启动约 14.7 秒，进一步表明首次渲染波动与剩余全文成本不可忽略。

还修正了一个随反复编辑积累的资源问题：屏外表格的部件可能从未挂载，因而也不会收到销毁回调。原先工厂在创建时就强引用它们；现在仅首次挂载才创建委托，卸载时退出活动集合。确定性工作量检查从“创建 1,000 个屏外句柄立即分配 1,000 个委托”变为 0，同时验证启停、卸载和重新挂载行为。

## 普通正文局部复用与三模式协调（2026-10-18）

本次继续优化以未保存文本、选区、阅读位置和历史一致为约束，保留 Source / Live 的共同语法与编辑会话。先处理可以证明展示不变的情况：在最后一个装饰之后编辑普通正文时，完整映射已有展示，不再先丢弃屏外装饰再全文重建；在同一普通正文行内移动折叠光标时，也保留完整展示。该路径要求前后语法树完整、段落结构与缩进不变、没有未知效果或手动块展示状态，并把资格检查限制在 4,096 字符以内。

这不是通用的 Markdown 块级增量渲染。装饰范围的位置映射不会自动更新 widget 内保存的绝对文本位置，因此文本编辑在后方仍有装饰、涉及复杂结构/原始辅助语法、巨大段落或无法证明一致时继续走现有完整更新路径。仅移动光标不会移动后续块的位置，所以同一普通行内的光标移动也可以保留后面的富文本块；真实编辑器和完整状态差分均覆盖此情况。没有把这种局部安全路径推广成所有输入都跳过重算。

真实编辑器回归先复现了普通尾部输入导致完整装饰数从 13 临时降到 10，以及只移动普通光标也重建全文的问题。现在首帧保持完整展示，结束输入直接复用；生产状态字段的插入、删除、空格、中文、多行正文结果与新建完整状态逐项一致，复杂辅助语法继续回退。测试同时覆盖立即离开待处理的 Live 输入、Source/Live 多次往返、选区和撤销/重做。

完整性标记也必须随资源更新失效：普通输入尚在等待刷新时，若资源或其他未知效果到达，不能因为文字展示已完整就跳过后续更新。新增真实本地链接状态变化回归，先复现缺失提示未更新，再验证输入结束后警告正确出现；相关记录为 `resource-pending-red.log` 与 `resource-pending-green.log`。

原生采样还发现另一层重复工作：链接状态响应先在消息路由中触发刷新，随后请求所有者更新缓存又刷新一次，即使结果完全相同也如此。现在由请求所有者在缓存真正变化后刷新一次，比较包含 Wiki 的问题提示；无变化和重复空结果不刷新。生产 `index.ts` 的 Source / Live 测试直接计数实际刷新方法，未变化结果由两次降到零次，状态/提示变化为一次；失败、重复失败、恢复及清空仍正确更新。这也减少 Source 与隐藏编辑载体的无效刷新。

三模式预算检查新增 Source / Live 未保存编辑、CDP 中文组合提交后立即进入 Preview，核对预览收到的全文与当前编辑版本完全相等，并验证返回后尾部仍在可见区域。检查等待编辑面移除遮罩与 inert 后才输入，匹配用户真正能操作的时机。相关原始记录为 `.local/phase-four/prose-red.log`、`caret-red.log`、`prose-differential.log`、`link-refresh-red.log`、`link-refresh-green.log` 和 `budget-final.log`。

原生对照使用综合样本副本，在末尾追加普通编辑目标，前后均通过文本、组合输入、保存、图表和滚动检查。单次采样中，进入 Live 约 3,812 → 1,960 ms，五次输入的 beforeinput 到两帧约 109–146 → 78–110 ms，撤销约 213 → 187 ms；Source 输入仍为几十毫秒。Preview 约 4.12 → 6.71 秒，尚无稳定改善证据。它们是两个本机样本，不是分位数；输入计时仍不包含 beforeinput 之前的事件排队。结果为 `.local/phase-two/tail-prose-baseline/result.json` 和 `tail-prose-status-final/result.json`。

中间版本的一次原生切换等待超过测试的 180 秒限制；另一次完成，但撤销约 1.14 秒，profile 中能看到历史与后台资源刷新连续执行。消除重复链接刷新后的上述运行通过，不能仅据此断言切换超时的根因已经修复。保留 `.local/phase-two/tail-prose-final/` 和 `tail-prose-mode-diagnostic/` 的失败/诊断记录。

## 自动启用与有工作量上限的部件重定位（2026-10-18）

这轮沿用已有的综合压力评估，不新增用户必须管理的开关。启动时仍综合 UTF-8 大小、行数、表格、图片、Mermaid 和公式数量；“快速打开大文档”设置仍只决定初始模式。新增运行时复评：累计修改达到 512 个 UTF-16 单元、行数相差至少 16 行，或上次压力已接近门槛时，在修改暂停 250 ms 后进入空闲队列。普通短输入不会因此增加全文评估。替换成更短但图片更密集的内容也会复评，判断不只关注长度增长。

策略调整等待组合输入、派生更新、滚动和按住控件的手势结束，隐藏或被模式切换遮罩覆盖的编辑面暂不调整；原生输入框聚焦时也暂缓。开启后本次编辑会话保持该策略，撤销缩小和 Source/Live 往返不反复重建；重新打开时按当前内容重新判断。当前模式、文本、选区、历史和阅读位置保持原有归属。运行中进入大文档策略会退出 Source 全文 TextMate 预热，使用已有的基础语法着色，并停止全文 Mermaid 预加载；Live 的延迟调度器同步采用大文档预算。适配发生在编辑提交之后，不保证首次巨大粘贴免除原策略已经开始的工作。

普通正文的安全复用扩展到了文档中部。仅移动装饰范围不足以保证正确：图片来源、复选框、代码选择按钮、公式和图表工具栏、HTML、表格单元格、脚注跳转还保存了源码位置。各部件现在通过同一个内部协议提供不修改旧值的位置映射，无法证明支持的类型仍回退。段落结构、缩进、完整语法树、单一折叠选区和展示上下文检查继续保留；换行、复杂语法、长段落、手动块状态及未知效果不走这条路径。

重定位过部件的编辑不会复用可能已经被挂载表格采纳过的旧历史检查点；撤销/重做重新生成准确坐标。尾部编辑等不改变部件坐标的情况仍保留原有检查点复用。挂载表格识别已应用到当前文档的投影，避免再次移动；文档标记使用弱引用，不延长旧文本版本的生命周期。同位置、同 side 的代码标签和操作按钮保留原顺序，避免仅重加其中一个导致工具栏换位。

性能验证否定了无上限推广。1 MiB 综合样本约有 94,834 个装饰，第一版全量重定位在五次输入中的同步耗时约 90–219 ms，慢于该次基线的 35–102 ms；尝试逐部件更新也更慢。最终仅在已有大文档策略中，对不超过 4,096 个装饰、512 个部件的完整展示启用中部重定位。超过预算继续使用原先的受限首帧和延迟完整更新；已经安全的尾部复用不受该上限影响。相关失败实验保留在 `.local/phase-five/full-scan-comparison.json` 和 `indexed-comparison.json`，没有将“减少重建次数”单独视为提速证明。

最终同条件对照使用约 92.9 KB、包含表格、公式、图片、HTML、代码及任务项的长文，固定在文档中部连续做五次独立输入。每次输入后的完整 Live 重建从 1 次变为 0 次；同步输入耗时中位数约 13 → 8 ms，16 ms 心跳观察到的最大间隔在五次采样中的中位数约 54 → 19 ms。Source 同批采样约 9 → 10 ms，没有稳定改善证据。该对照使用生产编辑器的程序化输入事务，包含文本发布和展示更新，但不是操作系统按键排队的端到端延迟，也不是跨设备或统计分位数承诺。记录为 `.local/phase-five/comparison.json`、`medium-final-comparison.log`。

## 明确的剩余范围

Live 仍通过状态字段维护会影响高度的全文块装饰；延迟全文重建会减少与连续输入竞争，但重建本身仍可能产生长任务。Preview 仍一次生成完整 HTML 和 DOM，按需图表和测量不会消除 HTML 解析与全篇 DOM 的成本。极端密度样本的首次 Live/Preview 打开仍可能达到秒级。

下一步若继续降低这部分开销，需要为块装饰做增量失效，并为 Preview 建立块索引及可取消的分批提交。本轮实验进一步说明：对所有部件逐个重定位仍随展示数量增长，不能替代真正的块级失效或相对块坐标。真正的块窗口化还要同时解决高度估计、滚动锚点、跨块选择、查找、复制、无障碍和导出，属于独立的架构阶段；不应通过硬裁文档或单纯增加等待时间实现。

当前停止投入的依据是：可明确复现的重复启动、重复扫描、重复几何测量和屏外资源强引用已经得到针对性处理，保留完整文本和既有编辑能力。下一步的主要收益需要改变全文派生更新与展示提交方式，改动面和验证成本会明显上升。更合理的后续目标是先独立验证 Live 块级失效或 Preview 分批提交中的一个，再决定是否扩大；目前没有证据支持把简单微调继续叠加为“极端混合文档已完全流畅”的结论。

成熟编辑器的官方资料、策略与限制见 [资料核对](large-document-research.md)。
