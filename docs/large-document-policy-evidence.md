# 大文档打开方式与自动策略：证据和决策

测量日期：2026-10-21。本轮在性能工作树上比较策略，并使用隔离 VS Code 验证真实打开行为；没有改动原始综合样本或用户的日常 VS Code 配置。

## 决策

**保留“优先源码打开”，默认关闭，默认沿用上次选择的模式。** 不把它作为全部性能优化的开关。保留旧配置键 `meoEnhanced.performance.largeDocumentOptimization` 和已有显式布尔值；未显式配置时使用新的关闭默认值。设置名称为“大文档打开方式：优先源码”，中英文说明均明确关闭后仍执行自动性能优化。

| 方案 | 判断 | 理由 |
| --- | --- | --- |
| 保留默认开启 | 不采用 | 性能已有改善，仍强制替换上次模式，会给日常使用带来意外 |
| 默认关闭、保留选项 | 采用 | 默认尊重模式偏好；慢机器、复杂样本仍能主动选用更快的 Source 打开 |
| 彻底移除 | 暂不采用 | 实际综合样本直接 Live / Preview 仍需数秒，没有证据证明该选择已无价值 |

这是一项体验取舍，并不表示冷启动已达到即时可用。用户显式开启过旧设置时仍保持开启，默认值修改不会覆盖显式偏好。

## 测量定义与限制

- 浏览器对照使用同一个生产入口、同一文档哈希和 1280 × 900 视口，轮换策略次序；每个直接打开使用新 BrowserContext、关闭 HTTP 缓存。暖切换在同一 Webview 会话完成。没有清空操作系统磁盘缓存。
- Host 渲染在独立 Bun 进程运行；浏览器对照不能代替 VS Code 的扩展 Host、资源协议和进程通信。另用原生 VS Code 探针验证 1 MiB 综合样本。
- 冷打开最终以工具栏和编辑区域退出 preload、目标模式就绪为准。先前“DOM 已生成”口径的结果仅用于发现问题，不作为最终可见首开耗时。
- 点击/输入耗时从测试端发出浏览器命令到确认光标或文本及两个动画帧，包含协议往返和主线程排队。它不是纯 input 事件处理耗时，也不能冒充硬件鼠标的精确延迟。
- 内存取渲染器 JS heap、DOM 节点及多次 GC 样本，不是 VS Code 总内存或整机 RAM。短时间的后台渲染、GC、JIT 和字体会造成波动。
- 自动测试同时检查源码内容、插入光标、延迟提交后的视口、格式证据和模式往返的文字位置。单次最终截图不能排除一帧闪烁；另有逐合成帧的输入呈现门禁。

可重复命令与原始结果均保留在本地 `.local/`。命令需要先完成 `bun run build:webview`；原生探针还需要扩展构建和已安装的 VS Code。

```powershell
bun scripts/benchmark-document-strategies.ts --confirm-long-run --rounds 2 --phase startup --strategies auto,synchronous --label final-startup
bun scripts/benchmark-document-strategies.ts --confirm-long-run --rounds 2 --phase interaction --strategies auto --modes live --label final-interaction
./scripts/benchmark-vscode-modes.ps1 -CaseFile <case.json> -CodePath <Code.exe> -ConfirmLongRun
./scripts/benchmark-vscode-startup.ps1 -Document <sample.md> -CodePath <Code.exe> -Scenario interaction -ColdInput
```

## 当前自动策略

压力值仍为：

`UTF-8 字节数 / 300000 + 行数 / 8000 + 富内容数 / 256`

| 处理 | 启用条件 | 与模式偏好的关系 |
| --- | --- | --- |
| 有预算的编辑派生工作、Live 视口呈现 | 压力 ≥ 0.25，或代码围栏 ≥ 48，或单表正文行 ≥ 512 | 不改变用户模式 |
| 轻量 Source 语法呈现 | 压力 ≥ 1 | 不由打开方式设置控制 |
| Preview 分块窗口及相应资源预算 | 压力 ≥ 1 | 不由打开方式设置控制 |
| 可选的 Source 初始打开 | 用户开启该设置，且压力 ≥ 1 或单表正文行 ≥ 1024 | 仅影响打开方式 |

不再让 `preferSource` 同时决定打开方式和渲染策略；它只属于打开偏好。Source 着色和 Preview 窗口分别使用明确字段。长表保护不会额外降低普通 Source 配色，也不强制普通 Preview 进入未经证明有收益的分块路径。

**这些数值是保守工程边界，不是已证明最优的分界点。** 本轮对照能证明复杂文档需要预算、单块规模不能只按文件大小判断，不能证明 300000/8000/256/48 是所有设备的最佳常数。不保留“普通 / 中等 / 较高压力”的固定产品分级。

围栏计数修正为识别无语言名、波浪线、引用和列表中的围栏，排除围栏正文中的图片、表格、公式和图表示例。以前 60 个无语言名围栏会被计为 0，另一些纯代码示例反而会被误计为富内容。新增最大行长、单围栏长度和单表行数诊断维度。识别仍是低成本启发式，不能替代完整 Markdown 语法树。

| 1200 | 1376 / 391 | 1222 / 416 |

## 常驻与按需策略

保持既有的局部更新、未变内容复用、CodeMirror 视口绘制和协作式时间预算。它们不应由“优先源码打开”控制。初始 Preview 的隐藏载体对所有文档使用 Source，避免先构建一个完全不可见的富文本表面；用户上次选择的可编辑模式独立保存。

保留按需的大型分块、Source 轻量语法和大范围后台工作策略。对小文档强制所有策略的收益并不稳定，而启动 Worker、准备索引、分块投影和维护高度也有开销，因此本轮不把所有大文档路径全量启用。

暂不增加根据整次点击/打开耗时来回切换“设备档位”的全局自适应策略。该耗时混合了加载、JIT、资源、系统负载和文档结构，会使同一文档的行为不稳定。继续采用结构准入和各执行器的实际时间片、输入安静窗口；在已有策略内让任务分片和让出主线程。后续如要增加自动切换，应先有能区分解析、DOM 提交、单块布局的归因数据，并采用滞回及会话锁定。

本轮还修复了长换行段落的阅读锚点：按当前可见文字位置恢复，而不是返回整个源代码行的开头；保留向 Preview 投影所需的段内进度。它属于模式协调的正确性修复，不依赖文件阈值。

首次直接 Live 的检查还捕获到真实回归：刚显示后立即点击正文输入数字，数字可能落在前一行。现已让初始 Live 使用与模式切换相同的结构准备条件，再恢复阅读位置并显示表面；没有加固定等待时间。生产回归先在旧构建失败，修复后连续 5 次首字符输入及长段落模式往返通过。

## 最终浏览器对照

Edge 155.0.4283.45。64 次直接 Live / Preview 打开、32 次完整输入与切换流程、16 次直接 Preview 后的首次可信滚轮流程全部通过功能与位置断言，不代表每个样本都达到流畅性目标。每类文档、每种策略各 2 轮；完整流程每轮每个编辑模式输入 8 个数字，检查准确源码、格式和实际阅读文字。1600 行长表还验证单元格前端数字插入、光标和 750 ms 延迟提交后的视口。

下面比较的是**自动策略组合**与强制同步/完整呈现组合，不能把全部差异单独归因于某一个功能。输入中位数受两个动画帧的测量下限影响。内存为模式往返后的最后 GC 点，两轮取中位数；每轮另取 3 个 GC 样本，未观察到采样窗口内持续增长，这不是长期无泄漏证明。

| 样本 | UTF-8 字节 / 行 | Live 输入中位数，自动 / 对照（ms） | Preview 快速跳滚最大帧间隔，自动 / 对照（ms） | JS heap，自动 / 对照（MiB） |
| --- | --- | --- | --- | --- |
| 小而简单 | 454 / 42 | 34 / 34 | 18 / 17 | 12 / 12 |
| 小而复杂，表格/图片/公式/图表 | 8809 / 672 | 50 / 51 | 18 / 18 | 20 / 20 |

Source 输入中位数各组约 33–34 ms，没有理由为它统一换用更重的策略。混合大文档的 Live 点击中位数为 49 / 433 ms，输入最慢样本为 115 / 384 ms；巨型代码块对照输入最慢达到 2619 ms，自动策略最慢为 66 ms。小而简单样本没有稳定收益，表格样本也没有内存收益。混合大文档最终 DOM 节点约 3758 / 132026，巨型代码块仍有 345587 个节点，说明整篇窗口化无法消除单块内部成本。

首次 Preview 滚动单独测量，不把“已显示”当作可交互：

| 样本 | 导航至确认首次交互，中位数，自动 / 对照（ms） | 观察 |
| --- | --- | --- |
| 小而简单 | 507 / 470 | 文档不够长，不执行滚轮；差异不足以支持全局加重策略 |
| 混合大文档 | 1110 / 15791 | 对照首次滚轮命令等了 11207–17468 ms，提前显示掩盖了后续阻塞 |
| 巨型代码块 | 4970 / 5265 | 两种组合仍需数秒；自动策略只是较早支付了部分布局成本 |
| 单个长表 | 791 / 806 | Preview 不提前分块也能得到相近结果 |

导航时间包含入口加载及探针往返，与前文初始化成本曲线不是同一口径。不同实验中的 JIT、资源和首次访问顺序会影响绝对时间：巨型代码块直接 Preview 的初始化就绪在另一轮达到 8.4–8.8 秒，不能用较快的一轮宣称它已稳定达标。

暖缓存也单列：混合大文档会话内首次进入 Preview 中位数约 449 ms，再次进入约 65 ms；对照约 339 / 238 ms。巨型代码块自动组合首次进入约 3951 ms，再次进入约 201 ms；对照把更多工作放到了初始隐藏预览中，不能仅凭其较快切换认为总成本更低。长表再次切入 Preview 两种组合都约 1.4 秒，仍是限制。

## 最终验证与剩余边界

类型检查、工作树及暂存快照的架构/测试清单、暂存隐私扫描通过。生产输入呈现门禁完成 804 帧合成画面检查，覆盖普通和大文档的正文、标题、列表、引用、脚注、代码、HTML、公式、LaTeX、Mermaid、表格及分栏预览；另验证原生输入会话的延迟提交、100%/125% 布局、冷预览对齐和巨型换行段落。Source 语法首屏、解析复用、运行时预算和设置交互矩阵也通过。设置页已做截图复核，标题和说明未被裁切；显式旧偏好保持可用。

本轮可以验收打开偏好与自动准入策略，但不能据此宣布整项性能工程结束。后续更值得处理巨型代码块和长表内部的呈现/布局成本，保留完整文本、选区、复制、查找和阅读锚点；继续微调文件大小常数无法消除这类单块阻塞。原生滚动条拖动仍需完成独立验收。

## 成熟编辑器的一手依据

VS Code 的 TextModel 以缓冲区字符长度和行数静态分类：大于 20 × 1024 × 1024 个字符或 300000 行，且启用 largeFileOptimizations 时，禁用昂贵的 tokenization；该分类在模型构造时锁定。另有默认 20000 字符的单行 tokenization 限制。这里的长度不是 UTF-8 文件字节，不应把其常数照搬到 Markdown Live。

- [VS Code TextModel 源码](https://github.com/microsoft/vscode/blob/main/src/vs/editor/common/model/textModel.ts)
- [VS Code 设置定义](https://github.com/microsoft/vscode/blob/main/src/vs/editor/common/config/editorConfigurationSchema.ts)
- [VS Code 大文件功能降级提示](https://github.com/microsoft/vscode/blob/main/src/vs/workbench/contrib/codeEditor/browser/largeFileOptimizations.ts)

CodeMirror 6 始终只绘制视口附近的 DOM，语言解析按视口和时间推进；扩展不能把完整语法树当作每次输入的立即前提。视口化仍不能消除一个巨型表格或超长单行本身的布局成本。

- [CodeMirror 视口设计](https://codemirror.net/docs/guide/#viewport)
- [CodeMirror visibleRanges](https://codemirror.net/docs/ref/#view.EditorView.visibleRanges)
- [CodeMirror 解析时间预算](https://codemirror.net/docs/ref/#language.ensureSyntaxTree)

以上支持“常驻局部机制 + 按功能成本保护 + 时间预算”的方向；不能直接证明本项目的具体阈值。本轮策略取舍以本地对照为依据，外部产品用于验证机制合理性。
